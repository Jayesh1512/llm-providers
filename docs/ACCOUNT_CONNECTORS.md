# Local account connectors

Implemented on 2026-10-10: wallet-authenticated API-key management with one-key OpenAI model discovery, and an official personal/local ChatGPT OAuth connector. Saves and consent are separate from on-chain discovery, offer publication and MON settlement. **Agent validation used no real account login, authenticated vendor model listing, token exchange, plan inference, paid validation or vendor marketplace authorization.** Tests use local credential fixtures, genuine locally signed RSA JWTs and mocked upstream responses. Live unauthenticated OpenAI discovery was checked; that is not a successful account registration.

Claude OAuth is unavailable: no authorized third-party client registration for this app was verified. Claude's working connector uses Anthropic Console API keys. Personal ChatGPT OAuth cannot serve supplier requests. Private OAuth remains blocked by Lit's missing hardware-authenticated Action/key statement and the absence of protected, rollback-safe mutable refresh storage. Consent or an environment flag cannot override these restrictions. TEE readiness is separately recorded in [PRIVACY.md](PRIVACY.md) and [ONCHAIN_ATTESTATION.md](ONCHAIN_ATTESTATION.md).

## Setup and ordinary host boundary

Use Node 22.12+ on a Unix host with owner-only filesystem permissions:

```sh
# Optional: preselect a PUBLIC management wallet in local .env (never its private key):
ACCOUNT_OPERATOR_ADDRESS=0xYOUR_MANAGEMENT_WALLET_ADDRESS
ACCOUNT_STATE_DIR=.account-state
ACCOUNT_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173,http://127.0.0.1:5174

npm run dev
# For an already-running local UI or static preview, run only its helper:
# npm run accounts
```

`npm run dev` starts both the UI and helper, reusing an already running compatible helper without stopping it or breaking its lock. The helper listens only on HTTP `127.0.0.1:8791`. The interface origin must match a configured loopback origin (localhost/127.0.0.1:5173 and the separate demo's exact http://127.0.0.1:5174 work by default; explicit ACCOUNT_ALLOWED_ORIGINS overrides that list, with no wildcard/LAN/hosted origins). On a fresh, empty directory, connect your wallet and sign the explicit “Initialize local account management for this wallet” challenge; only a valid signature pins the first owner. Unsigned wallet claims do not initialize it. Signature verification and the atomic owner write enforce the pin even during concurrent claims. Existing credentials without an owner cannot be claimed through this route; recovery needs explicit trusted local configuration.

Subsequent management challenges use the pinned owner. `ACCOUNT_OPERATOR_ADDRESS`, or `PROVIDER_ADDRESS` when unset, can preselect that public owner. A missing `.env` no longer prevents fresh setup. The signature creates a ten-minute, in-memory bearer session, not an on-chain transaction, encryption key or escrow approval. Changing wallet configuration does not transfer an existing directory to another wallet. The first-owner setup assumes the local OS/process environment is trusted; configure the owner in advance when that is preferable.

For API keys used by a supplier, that management wallet must equal the provider-owner `PROVIDER_ADDRESS`, which may differ from the node's authorized signing operator. Point both helper and provider at the same `ACCOUNT_STATE_DIR`. The wallet controls management authorization; local OS administrators can still read ordinary host credentials and personal prompts. This is not Lit/TEE credential storage. Credential files are plaintext in an owner-only directory (`0700`), atomically written with `0600` permissions, file/directory fsync and a single-writer lock. OAuth and API secrets are in separate files; the provider resolver reads only the API-key file.

No existing Codex/Claude credential files, Keychain entries or signed-in accounts are imported. No secrets enter browser storage, on-chain offers, logs, public health responses or management-list replies. API-key form input and personal prompts are transient browser memory. Do not run the helper under a shared/untrusted OS account.

## API-key connections

For normal OpenAI setup, paste a key into the password field and explicitly save/connect. Authenticated save accepts `{provider:'openai',baseUrl:'https://api.openai.com',apiKey,discoverModels:true}` without a manually typed model. It writes **one** protected credential, then requests only `GET https://api.openai.com/v1/models` with that key. The endpoint and provider are explicit; key prefixes do not select a provider. HTTP redirects are rejected. This retrieves [catalog metadata](https://developers.openai.com/api/reference/resources/models/methods/list), without an inference or billed validation call. A list result proves catalog visibility at discovery time; it does not prove inference eligibility, available credit, quotas or access to every OpenAI model. Returned inference validation is always **unverified**.

The returned `catalog.models` is the intersection of the key's actual vendor IDs with reviewed text-input/text-output Responses adapter capabilities, preserving exact IDs and upstream order. [openai-catalog.ts](../src/accounts/openai-catalog.ts) records 83 exact aliases/snapshots reviewed against 49 official model pages on this date. This policy is separate from the UI's popular-model suggestions, and never generates availability from them. Fine-tunes, image/audio/embedding/moderation models, specialized research/tool paths, legacy instruct endpoints and unreviewed IDs appear in `catalog.unsupported`, with no selectable node config. New or unusual text IDs need capability review before inclusion; a matching prefix is insufficient. The synchronous adapter's timeout/output limits still apply, and even a listed supported model can be rejected by upstream account permissions or billing. No discovery result is called inference-tested.

Each catalog model contains a secret-free `providerModelConfig` with `model:'openai/'+exactID`, `upstreamModel:exactID`, `apiKind:2`, and the **same** opaque `authentication.credentialRef`. No model is implicitly selected on a catalog credential. Explicitly select configurations in local `PROVIDER_MODELS_JSON` and restart the provider; configure separate native test MON input/output rates and explicitly publish matching offers. The returned `apiKeyEnv` is empty; an environment key and managed ref cannot both be selected. Saving, metadata discovery and preparing an offer neither publish a transaction nor run inference. Existing environment-variable models continue to work.

Discovery failures retain the saved key/ref and return `catalog.status:'failed'`, a fixed error category and empty model lists; retry with only the ref. Explicit rediscovery clears old membership before the network call, so a failed refresh cannot authorize an old cached model. Cached membership is persisted, not automatically refreshed or an enduring vendor permission proof. Removing a key or locking/expiring management aborts pending metadata discovery; late results cannot resurrect removed or canceled catalog state. Browser views/prepared selections must be cleared on lock, wallet change, removal or failed discovery. No catalog or credentials belong in browser persistent storage.

Anthropic, compatible and existing manual OpenAI bindings retain the earlier `{provider,model,upstreamModel,baseUrl,apiKey}` save path with no vendor network call. Anthropic/OpenAI require official origins; compatible APIs allow an explicit HTTPS prefix without URL credentials/query/fragment. Manual records return optional legacy `providerModelConfig`. They are not automatically migrated. Explicitly discovering an existing OpenAI ref upgrades it to a catalog credential, preserving its secret/ref but replacing its manual binding: custom public aliases stop resolving; select the returned exact `openai/<id>` configs and update/pause affected offers deliberately.

The standard provider checks the stored provider-owner, connector kind, exact local/upstream IDs, capability/API kind, base URL and current cached catalog membership before supplying a catalog key. It re-reads the atomic API-only snapshot for each paid call; manual records keep their exact original binding. A removed, mismatched, unsupported or failed-catalog ref blocks the call without environment fallback. Public health omits refs/secrets. Removal clears the key/catalog and blocks future resolution; it does not revoke the upstream key, unpublish offers or cancel an already submitted paid inference. Revoke vendor keys separately when appropriate.

Host-managed references cannot be used as protected Lit credentials. Private API keys require the existing explicit sealed-envelope preparation against an approved immutable Action and its account commitment. No such live release is approved today.

## Personal ChatGPT OAuth

The connector follows OpenAI's current [open-source token-sharing sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [profiles and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) and [models/inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) contracts. It does not use OmniRoute's borrowed Codex CLI client identity or `chatgpt.com/backend-api/codex/responses` endpoint.

1. The helper starts a fresh ephemeral `http://127.0.0.1:<port>/auth/callback` listener before opening consent. First consent uses `dynamic_agent_client`, the app's actual `LLM Providers Personal` name and a persistent opaque host UUID. Returning consent uses the previously issued `oaiapp_…` client registration.
2. Each attempt has fresh S256 PKCE, state and nonce, a five-minute maximum lifetime and an originating management-session binding. The exact redirect, issuer when supplied, single-use state, issued client and returning subject are checked. OpenAI's documented optional callback `scope` is accepted as informational only; duplicates, oversized values and unknown query parameters still reject. Permissions come from the authenticated token response, never callback scope. The callback consumes the attempt before code exchange and redirects to a clean completion path. Closing/expiring management or disconnecting prevents a pending attempt from publishing credentials.
3. `jose` verifies the ID token's RS256 signature against official HTTPS JWKS, issuer, audience/authorized party, nonce, subject, issuance and expiry. Identity-only consent is stored as `permission_required`; inference requires actual granted `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct` scopes. ID tokens and email hints are not placed in the browser's consent URL.
4. Access/refresh/ID tokens remain in the OAuth-only credential file. Refresh uses the issued client ID, the official resource, rotating refresh tokens, serialized per-registration operations and durable pre-rotation markers. Ambiguous transport loss, invalid/reused tokens, identity/scope changes or malformed rotation require reconnect. A confirmed transient server failure preserves credentials with backoff. After an interrupted rotation/revocation the old refresh token is discarded on restart; orphan snapshot files are removed before serving the directory.
5. The helper retrieves the actual account model catalog and preserves listed exact slugs/order. A user explicitly chooses a model and sends a personal prompt to the public `https://api.openai.com/v1/responses` endpoint with bearer OAuth, `store:false` and `stream:true`. There is no CLI impersonation, alternate backend or automatic API-key retry. A completed Responses stream, valid upstream usage and the selected model are required; deltas, failed/incomplete streams, truncation and quota/rate failures produce no successful result or invoice.
6. Disconnect aborts active personal inference, attempts official remote session revocation, then durably removes all local tokens. Validated registration identity is retained to reconnect using its issued client ID. If remote revocation cannot be confirmed, the UI directs the user to disconnect the app in ChatGPT settings. Bare HTTP 401 does not automatically prove account revocation.

Only masked identity/workspace-registration labels are returned. The label distinguishes issued registrations; it is not a decoded or invented workspace name. Statuses include connected/expired, refreshing, reconnect/permission required, unavailable/restricted, rate/quota limited and signed out. The helper does not infer remaining subscription tokens, convert quota to MON or promise savings. Account plan/credit use is controlled in ChatGPT settings and is separate from marketplace MON invoices. Personal results are explicitly `marketplaceInvoice:false` and ordinary-local-host privacy.

OpenAI's [token-sharing documentation](https://developers.openai.com/siwc/token-sharing-open-source) directs paid/remotely hosted products to an interest/approval path. No registration authorizing this marketplace's supplier resale was established. The production supplier core, startup credential check and adapter reject ChatGPT OAuth even for valid funded requests. Claude's [official third-party account policy](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account) directs ordinary third-party products to Console/cloud APIs; limited vendor-authorized credit integrations are not general permission to route marketplace traffic through Pro/Max limits. A working OmniRoute implementation is not evidence of our authorization.

## Management API and recovery

All routes require exact `Host`, configured loopback `Origin`, bounded strict JSON and no query parameters. `/accounts/info` reports the public operator (null before setup) and `initializationRequired`. POST `/accounts/challenge {}` uses the pinned owner; only when uninitialized it requires `{operator: connectedWallet}` and returns `initializing:true`. POST `/accounts/session {challenge,signature}` checks the one-use EIP-712 `LocalAccountAccess` signature and pins an uninitialized owner atomically. Its domain is `LLMProvidersLocalAccounts`, version `1`, chain `10143`, zero verifying-contract address; the message binds helper service ID, origin, random challenge, expiry and explicit initialization/management purpose. This is distinct from funding/inference signatures. All following routes require the Origin-bound bearer session:

| Route | Input / result |
| --- | --- |
| GET `/accounts/status` | `{accounts: ConnectedAccount[]}` masked OAuth metadata |
| POST `/accounts/connect` | `{provider,usage,privateMode,credentialRef?}` → `{attemptId,authorizationUrl}`; unsupported use rejects before accessing credentials |
| POST `/accounts/attempt` | `{attemptId}` → `{status: pending\|connected\|rejected,diagnostic?: {stage,reason}}` for that management session; fixed enum codes only |
| POST `/accounts/disconnect` | `{credentialRef}` → `{remoteRevocationConfirmed}` |
| POST `/accounts/models` | `{credentialRef,usage:'personal-local',privateMode:false}` → exact listed models |
| POST `/accounts/infer` | Above plus `{model,prompt,maxOutputTokens}` → result/usage, plan billing source, no marketplace invoice |
| GET `/accounts/api-keys` | `{credentials: ApiKeyConnection[]}` masked unverified metadata |
| POST `/accounts/api-keys/save` | `SaveApiKeyInput` → `{credential: ApiKeyConnection}` without secret |
| POST `/accounts/api-keys/discover` | `{credentialRef}` → `{credential: ApiKeyConnection}`; official OpenAI metadata only, no secret re-upload |
| POST `/accounts/api-keys/remove` | `{credentialRef}` → `{removed:true}` |
| POST `/accounts/lock` | `{}` → invalidates management session, pending consent and its metadata discovery |

Types are in [shared/accounts.ts](../src/shared/accounts.ts). There is no token-import endpoint, arbitrary OAuth redirect/origin configuration or provider-wallet decryption access condition. Browser management sessions stay in memory and are fenced on wallet change/lock. Errors expose fixed messages, not JWTs, codes, prompts, vendor bodies or credentials.

OAuth rejection diagnostics distinguish callback/state/redirect/client validation, token exchange, JWKS/JWT identity checks, token schema, storage and attempt lifecycle. Only fixed `stage`/`reason` enums are returned; exception text, upstream bodies, JWT claims, codes and request URLs are never included or logged. Unavailable JWKS, wrong signatures/issuer/audience/nonce, invalid schemas and storage failures remain rejected. Failed callbacks redirect to a clean `/auth/rejected` path showing only the bounded diagnostic. Invalid pre-exchange callbacks cannot consume legitimate pending state; valid-state attempts are single-use before exchange. Outcomes expire in memory and are management-visible only to their originating session.

For a real rejected login, report only its fixed stage/reason, not its callback URL. `/accounts/info` publishes non-secret runtime ID `catalog-oidc-diagnostics-20261010-1`, catalog protocol and diagnostic version, distinguishing a stale helper from tested source. The two earlier live rejections cannot be retrospectively diagnosed from generic outcomes; only the first scope-whitelist bug was identified. Public OpenAI OIDC discovery and JWKS returned HTTP 200 with the pinned issuer/endpoints and RS256 keys. That checks metadata/connectivity, not an account token or completed login. A fresh user-controlled attempt is needed to collect the second failure's cause; no identity checks were disabled to force completion.

After an unclean shutdown, confirm no helper process owns the directory before removing only its stale `.lock` and, if present, `api-keys/.lock`. Preserve credential/state files; startup clears ambiguous refresh state automatically. Locks are deliberately not broken automatically. Reconnect resolves lost refresh capability; do not restore an older credential snapshot to reuse a rotated token. Current ordinary files cannot provide hardware rollback resistance and are not used for private OAuth.

## Validation and external prerequisites

The mocked tests exercise cryptographic JWT signatures and wrong key/algorithm/issuer/audience/authorized-party/nonce/time, PKCE and documented scoped callbacks, origin/wallet/service/chain replay, account/client substitution, granted scope restrictions, refresh concurrency/rotation/terminal and ambiguous failure, restart recovery, logout, redaction, stream truncation/tampering/quota and private/marketplace fallback denial. Catalog tests cover authenticated save-once/discovery/ref-only retry, exact visible-vs-capable filtering, same-secret multiple configs, owner/origin/API/model/ref substitution, HTTP/malformed/duplicate/oversized/reflected-secret metadata, failure invalidation, cancellation/removal races, legacy migration and protected restart. The actual HTTP browser client is tested with fixture keys for request authorization and generation fencing on lock. Existing adapters, invoices, escrow and encrypted fixtures remain regression coverage.

Validation snapshot on 2026-10-10: 68 TypeScript tests, 29 Foundry tests, type checking, the production build and standard/private Anvil end-to-end tests passed. Diagnostic tests also verify stage-specific exchange/JWKS/signature/nonce/audience/time/schema/storage failures, clean rejection-page redirects and secret redaction. Startup tests cover a real listener without wallet environment configuration, safe reuse without stealing locks, signed initialization/owner races, and official consent URL generation through the actual HTTP client. The real running browser reached the helper and its initialization-signature request; the diagnostic deliberately stopped before signing or login so it did not claim the user's directory. A provider HTTP integration used a selected saved key for a funded/signed fixture request and produced its normal signed invoice; removing the key blocked later requests. Its API response was mocked, with no real billing. The rebuilt Lit example is still unapproved, not an operational private gateway.

Live consent requires an eligible ChatGPT account, the official dynamic registration/scopes and the user's fresh approval. No account login or quota spend was performed to finish these tests. Claude OAuth needs actual vendor-approved registration. Marketplace OAuth needs separate vendor authorization for paid remote resale. Private OAuth needs Lit's authenticated runtime→Action→key evidence, the approved immutable runtime/Action/channel and protected durable anti-rollback rotation/revocation storage before any tokens can be sealed or used there. Neither an API-key save nor OAuth success makes the blocked TEE flow ready.
