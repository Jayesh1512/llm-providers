# Lit private inference: implementation and release boundary

**Status: local integration and on-chain verifier code exist; usable live private inference is blocked.** Current Chipotle evidence does not authenticate the Action CID and HPKE/action keys in a hardware-signed, challenge-bound statement. The new contracts reject that missing binding. Consumer release approvals are empty. No live private funding, paid Lit execution, public contract deployment, or end-to-end hardware privacy validation has been performed.

The selected backend is current Lit Chipotle, not AWS Nitro. Our registry, escrow and attestation verifier target **Monad testnet 10143 only**. Explicit local simulations use 31337. Lit's existing permissions/root KMS use **Base 8453**; our marketplace does not move to Base. A read-only Chipotle `get_node_chain_config` call returned Base 8453 and third-party contract `0xaaaaa9120fe271f653cfdb6bf400db93d2dea7aa`. This is an external dependency, not a project deployment or a Monad-native KMS claim.

## Intended trust boundary

The browser holds prompt salts and ephemeral consumer response private keys. An immutable, independently approved Lit Action holds the derived action scalar and HPKE decryption key inside the approved protected runtime. The supplier's ordinary node never handles plaintext inference; the consumer connects through its own local verifier to Lit. The action alone decrypts, validates funding and authorization, claims the request once, performs authenticated upstream HTTPS, and returns HPKE ciphertext. The approved code and upstream LLM process plaintext. Request identities, lengths, timing, rates and settlement token counts are not concealed.

Protection depends on Intel TDX/DCAP, the reviewed Lit runtime and action, Phala/dstack verification and hosting, Lit KMS/governance on Base, proof-system soundness, and the consumer's trusted browser/local machine. It does not protect against compromised approved code, upstream access to content, a compromised consumer, or compromise of Lit's key infrastructure. Governance-approved runtime changes can threaten historical keys; independent pins and revocation matter. No claim is made about an underlying hosting provider that has not been established by evidence.

The full on-chain policy, missing Lit binding, program identity, root pins and governance semantics are detailed in [ONCHAIN_ATTESTATION.md](ONCHAIN_ATTESTATION.md). A provider signature or a published key is never hardware attestation.

## Content protocol

The strict public privacy configuration contains version 1, backend `lit-chipotle`, immutable action CIDv0, uncompressed secp256k1 action public key, independently selected runtime policy ID, and approved models. Each model pins the exact upstream model, adapter, official HTTPS origin, account-policy ID and secret-salted credential commitment. Its hash is Keccak256 of a fixed ordered JSON tuple; `src/privacy/protocol.ts` is the canonical encoder. Unknown fields, duplicate models, arbitrary origins and compatible Chat Completions are rejected.

Each session's fixed tuple includes version, chain ID, registry/escrow, provider/operator/consumer, offer ID, privacy configuration hash, funded request ID, prompt commitment, output limit, random challenge, response-key fingerprint and issuance time. Addresses normalize to lowercase. `contextHash` is Keccak256 of this encoding. Sessions expire in 60 seconds. Request ID zero is public key setup/pre-funding only and cannot infer.

HPKE uses `@hpke/core`'s RFC 9180 DHKEM(P-256, HKDF-SHA256), HKDF-SHA256 and AES-256-GCM. Content authenticates the full session as AAD and fixed direction-specific info (`request`, `response`, or `credential`). Request envelopes contain `{enc,ciphertext}` only. The encrypted payload contains prompt, secret prompt salt, consumer signature and response SPKI public key. The action checks its fingerprint against the signed/AAD context. Answer text, response salt, metering and the operator-signed invoice are encrypted to that consumer key. There is no plaintext fallback.

The action HPKE key is deterministically derived **inside Lit** from its current immutable-action scalar with domain-separated WebCrypto HKDF and RFC 9180 `DeriveKeyPair`; the scalar and seed are never returned. This keeps credentials usable across stateless action invocations. Changing action bytes/manifest changes CID and action keys. The consumer response key is ephemeral per session. No key is derived from a public wallet signature; no wallet private-key export is requested.

A `GatewayKeyBinding` EIP-712 action signature binds context hash, configuration hash, action-ID hash, encryption SPKI fingerprint and issuance time under the intended chain and escrow. It is an action identity proof over an independently verified protected channel, not a TDX quote. The browser signs `PrivateInferenceRequest(requestId,promptHash,maxOutputTokens,contextHash,enclaveKeyHash)`. Both client and action verify every relevant binding. The escrow authenticates this same consumer authorization at private acceptance against the funded encryption-key fingerprint and stores the signed session hash.

Commitments are `keccak256(abi.encode("LLMProvidersPrivate:<kind>:v1", domain, secretSalt, text))`, with independent 256-bit salts. Prompt/response domains are the configuration hash. Credential domain is the provider/model offer ID, avoiding a circular dependency between credential commitment and action CID. Prompt salt stays on the consumer machine and encrypted channel; response salt is inside the encrypted invoice. Secret salts, API keys, wallet/encryption private keys and plaintext never enter contract calldata/events/configuration.

Blockchain supplies public identity, configuration and funded-request integrity. It does **not** encrypt/decrypt confidential prompts or store a shared secret. Public fingerprints and commitments are integrity evidence, not decryption secrets.

## Consumer verification and execution

`src/privacy/lit-channel.ts` uses pinned `@lit-protocol/keychain` 2.2.3 to check the current Chipotle TDX signature chain, measured event log, application/images, Base-governed KMS whitelist and TLS certificate evidence. The consumer independently pins exact MRTD/RTMR values, app ID, compose/OS/KMS identity and runtime-policy ID. No provider endpoint can supply these approvals.

The SDK omits full Intel collateral, TCB/QE identity and revocation verification. Production therefore additionally requires an independently reviewed **full dstack/DCAP verifier executable**, pinned by SHA256 and absolute path. It must verify both `/attestation` and `/evidences/quote.json`, including collateral/revocations. The client requires verified quote/event-log/OS flags, exact `UpToDate` TCB, no advisories and matching report data; `is_valid:true` alone is insufficient. Development OS results are rejected. The quote measurements must match the independent policy, and debug quotes are refused. Runtime event-log digest normalization follows the current primary documentation. Installing an arbitrary provider-supplied executable is not approval.

The current app quote's REPORTDATA does not contain a consumer nonce; the separate evidence quote binds a checksum list containing the TLS certificate. The client does not pretend these are arbitrary nonce-bound statements. It pins the attested leaf certificate **on every actual HTTPS API connection**, checks normal CA/hostname validity and forbids redirects. Fresh TLS proof of key possession, the random action-signed session challenge, and the independent on-chain challenge binding serve different purposes. All remain required.

The consumer-owned loopback helper binds `127.0.0.1:8790`, exact Host and explicitly allowed frontend Origins. The browser ignores provider URLs for private execution. The helper checks action source bytes/CID, independent approvals and fresh verification before `/core/v1/lit_action`; the execute-only billing key stays outside Vite/browser code. Current API requests use `code`, `js_params`, `X-Api-Key` and `X-Privacy-Mode: true`. All inference and credential inputs crossing this helper are ciphertext. No general decrypt/key-export/signing operation exists. `bootstrap` exposes only a signed public-key binding for provisioning; it cannot approve a release, fund, claim or infer.

The immutable action reads Monad 10143 funding/registry state through the fixed official RPC, verifies consumer authorization, and mines a `claimPrivate` transaction before making a paid upstream call. The action-derived operator needs test MON for that transaction. Public RPC availability and correctness are dependencies; the action checks chain ID, contract code and registry linkage. This prototype does not implement a Monad light client inside Lit. Transaction nonce collisions between concurrent stateless invocations can cause safe failure; only a mined successful one-shot claim permits an API call.

Private processing uses ephemeral memory only. It has no host journal, recovery endpoint, arbitrary origin, configurable fetch proxy, prompt logging or plaintext errors. The HTTP gateway/relay in `src/privacy/server.ts` is **a local test harness only**, with no production entry point. Running that gateway on an ordinary Node host provides no TEE protection. The production action has no test injection parameters.

If the action dies after claiming, the answer is lost, or limits are exceeded, it will not issue another paid call for that request. The consumer can refund after expiry if unsettled; the supplier may lose its upstream cost. Private answers remain in browser memory and are not written to localStorage. Private sessions save only recovery/payment metadata and the consumer's prompt salt. Invoices are signed; the existing explicit consumer usage approval settles directly through the wallet. Honest model identity, metering and fair exchange are not proved.

## Upstream policy: default blocked

| Adapter | Enforced behavior | Additional independent approval required |
|---|---|---|
| Anthropic Messages | Only `https://api.anthropic.com`; exact model; no arbitrary proxy, redirects or user headers | Account/model retention and content-access policy; supplier cannot enable/access logs, debug features, support exports or organization dashboards exposing content |
| OpenAI Responses | Only `https://api.openai.com`; exact model; `store:false`; no retrieval route, background/storage options, redirects or arbitrary headers | Suitable approved account/model retention policy, including abuse-monitoring content access; supplier cannot change settings or access content logs/dashboards/support exports |
| Compatible Chat Completions | Rejected in privacy mode | No verified universal endpoint/account policy; standard mode remains available |

`store:false` alone is not a no-content-access guarantee. A supplier claim, a model name or a policy hash does not establish account governance. Approved credential commitments prevent swapping in another logging account, but cannot prevent an account owner changing retention or content-access settings. If the supplier can do that, **do not approve that configuration**. There are currently no approved account/model configurations. The allowlist remains empty even if basic Lit connectivity succeeds.

## Reviewable setup tools

The example manifest in `docs/examples/lit-action-manifest.local-example.json` contains dummy addresses and zero credential commitment. It is for local bundling only; never approve or deploy it.

```sh
npm run privacy:build -- docs/examples/lit-action-manifest.local-example.json
npm run privacy:check-monad          # read-only proof/precompile/size checks; no deployment
```

For a real proposed release, first independently establish account governance and allowed exact models. On a trusted local machine, set `UPSTREAM_API_KEY` without putting it in chat or Vite variables; run `privacy:credential -- <provider> <model> .privacy-secrets/credential.json`. It writes key/salt with mode 0600 and prints only the public commitment. Put that commitment and public network/model/account-policy values in the immutable manifest, then build. Combine private credential files into an array inside `.privacy-secrets/`.

`privacy:prepare -- privacy-artifacts/release.json trusted-runtime.json .privacy-secrets/credentials.json .privacy-secrets/candidate.json` requires a pinned full verifier and `LIT_USAGE_API_KEY` with execute-only scope and prepaid Lit access. **This explicit preparation command executes billed public-key/bootstrap actions when run**; it does not provision an account or buy credits. It verifies the runtime/TLS, looks up the exact action key, validates a fresh public-key binding and HPKE-seals the pinned credentials. It writes a candidate configuration, never auto-approves it. This command was not run against live Lit in this implementation.

To become usable, the release also needs the missing Lit hardware/action/key evidence and a genuine current proof for the pinned DCAP guest. `privacy:attestation-call` prepares unsigned Monad wallet calldata for global configuration, challenges or proof submission; it sends no transaction. Registry governance must independently approve measurements and configure the verifier once. Suppliers may then publish only a valid verified policy. Do not configure current Lit measurement values as though they implement the missing binding API.

After those prerequisites and independent code/account review, explicitly add the approved configuration hash to consumer-owned `src/privacy/trust.ts` and rebuild the frontend. Start `privacy:client -- .privacy-secrets/candidate.json` on the consumer machine, then select private mode. Private funding additionally requires valid on-chain attestation, and the client re-verifies a fresh protected session after funding. Standard mode stays available and explicitly says the supplier can read prompts and answers.

## Validation evidence

Tests cover HPKE round trips, salted/verifiable invoices, ciphertext/key/context substitution, cross-request/chain/contract replay, malformed wallet signatures, signed-key freshness, invalid runtime pins, rejected plaintext routes/fallback, credential substitution and production action bundling in a sandbox without Node APIs. Local Anvil exercises funding, accepted-key/session-bound claims, replay across restarts, settlement, withdrawals and refunds. Local mock verifiers and action keys are explicitly simulation-only and cannot be installed on Monad 10143.

Final local checks on 2026-10-10: **29 Foundry tests** (including 256 cost-fuzz runs), **49 TypeScript tests** (including the subsequent local account connectors and UI tests), the standard/private Anvil integration, production build and immutable action bundle passed. An actual browser WebCrypto round trip and cross-chain/unapproved-release rejection also passed. The updated example bundle is 847,064 bytes, below the current 1 MB action source limit; its CID is `QmeWJFoR3yTnHU2wXHk7RueZbNqfwQpsaYqEwELsbHDgUJ` and it remains an unapproved local artifact. Host-managed API-key refs and ordinary OAuth are rejected by the protected gateway; no account connector enables private fallback. The Rust prover passed API/type checking with native kernels skipped; its normal executable build needs the missing Metal toolchain and a working Groth16 environment. Read-only Monad cryptographic proof/gas checks and the distinction between archived evidence and production acceptance are recorded in [ONCHAIN_ATTESTATION.md](ONCHAIN_ATTESTATION.md).

Foundry authenticates official RISC Zero and archived Automata DCAP Groth16 receipts, rejects altered proofs/program roots and tests all contract policy gates. The archived hardware proof is rejected by the production program/policy. Upstream zkDCAP's 23 native Rust unit tests passed, including published Intel TDX/SGX quote fixtures. A current public Lit quote passed diagnostic signature-chain checks; full current collateral verification, action identity execution and protected upstream inference were **not** validated live.
