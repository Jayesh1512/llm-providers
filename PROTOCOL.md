# MVP protocol

Paid API inference only. Local-model adapters are future scope. Public deployments must be Monad testnet, chain ID 10143. Chain 31337 is allowed only for explicit local testing. Suppliers expose a public HTTPS node; loopback HTTP is allowed for local development. Discovery reads PeerRegistry directly; no DHT or central directory is authoritative.

## Contracts

`PeerRegistry` has `register(uint8 roles,address operator,string endpoint,string metadataURI)`, `setActive(bool)`, `getPeer(address)`, `peerCount()`, `peerAt(uint256)`. Roles 1 provider, 2 consumer, 3 both. Peer: `{ roles, active, operator, endpoint, metadataURI }`. Supplier owner wallet controls the listing; operator is a separately authorized node signing address. Consumer may have zero operator and empty endpoint.

`setOffer(string model,uint8 apiKind,uint256 inputPrice,uint256 outputPrice,bool active)` upserts an offer identified by `keccak256(abi.encode(provider,model))`. `getOffer(bytes32)`, `offerCount()`, `offerIdAt(uint256)` enumerate. Offer: `{ provider, model, apiKind, inputPrice, outputPrice, active }`. API kinds: 1 Anthropic Messages, 2 OpenAI Responses, 3 OpenAI-compatible Chat Completions. Namespaced model IDs are supplier-chosen; the upstream exact model ID is private node config. Prices are native test MON wei per 1,000,000 input/output tokens. No claimed guaranteed discount.

`InferenceEscrow(registry)` exposes `fund(bytes32 offerId,bytes32 promptHash,uint64 expiresAt) payable -> uint256 requestId`, `getRequest(uint256)`, `settle(uint256 requestId,uint256 inputTokens,uint256 outputTokens,bytes32 responseHash,bytes consumerSignature)`, `refundExpired(uint256)`, `credits(address)`, `withdraw()`. Request: `{ consumer,provider,offerId,promptHash,deposit,inputPrice,outputPrice,expiresAt,closed }`. Prices snapshot at funding. IDs start at 1. Funding deadline 60 seconds to 1 day in future. Charge ceiling `(inputTokens*inputPrice + outputTokens*outputPrice)/1_000_000`. Settlement credits provider and consumer unused deposit, closes once; any caller may relay, payouts fixed. Buyer signature authorizes charge. Expiry allows refund; withdraw uses pull payments.

`RequestFunded(uint256 indexed requestId,address indexed consumer,address indexed provider,bytes32 offerId,bytes32 promptHash,uint256 deposit,uint64 expiresAt)` provides the request ID in funding receipts.

EIP-712 domain for inference auth and consumer usage approval: `{name:'PeerTokensEscrow',version:'1',chainId,verifyingContract:escrow}`. Types: `InferenceRequest(uint256 requestId,bytes32 promptHash,uint256 maxOutputTokens)` and `UsageReceipt(uint256 requestId,uint256 inputTokens,uint256 outputTokens,bytes32 responseHash)`.

## Direct peer protocol

`GET /health` lists configured model IDs/public peer identifiers, no secrets. `GET /identity?challenge=<random bytes32>` returns `{provider,operator,signature}` with EIP712 `PeerIdentity(bytes32 challenge,address provider,address registry)`; domain `{name:'PeerTokensIdentity',version:'1',chainId,verifyingContract:registry}`. Buyer verifies operator equals the on-chain peer operator before funding or transmitting a prompt.

`POST /infer`: `{requestId:string,prompt:string,maxOutputTokens:number,signature:hex}`. Node checks chain funding, supplier ownership, active registration, configured model/API format, prompt hash, consumer inference authorization and budget/deadline before running its configured upstream API. Response: `{requestId:string,text,inputTokens:number,outputTokens:number,responseHash:hex,amountWei:string,provider,operator,signature:hex}`. Invoice signature EIP712 domain `{name:'PeerTokensInvoice',version:'1',chainId,verifyingContract:escrow}` and `Invoice(uint256 requestId,bytes32 responseHash,uint256 inputTokens,uint256 outputTokens,uint256 amountWei)`.

`POST /settle`: `{requestId:string,inputTokens:number,outputTokens:number,responseHash:hex,signature:hex}` relays the consumer UsageReceipt; returns `{transactionHash}`. Operator signs transaction; provider wallet receives credit. Consumer approval is explicit and binds response hash. Contracts do not prove model identity, upstream honesty, or answer quality. Suppliers bear nonpayment risk when consumers withhold usage approval; this prototype does not solve fair exchange.

Standard API credentials stay on supplier nodes. The private path seals credentials inside an approved Lit Action. OpenCode is a client/gateway ecosystem, not an underlying LLM; compatible paid endpoints can be configured without claiming OpenCode itself generates tokens. Prompts and responses never go on-chain; only their hashes are stored or signed. Native test MON has no enforced USD conversion; this is testnet accounting.

## Prepaid API keys

`openPass(address provider,bytes32 keyHash,uint256 maxInputPrice,uint256 maxOutputPrice,uint256 maxCallCost,uint64 expiresAt) payable -> passId` deposits once for one provider (expiry up to 30 days). `keyHash` is `keccak256` of a 32-byte secret the consumer generates; only the hash is on-chain. The API key is `pt_<passId>_<secretHex>`. `chargePass(passId,offerId,callId,inputTokens,outputTokens)` is callable only by the provider's registered operator. Cost is computed on-chain from the offer's current rates, and reverts above the pass price ceilings, above `maxCallCost`, above the unspent deposit, or on a reused `callId`. `closePass(passId)` is callable by the consumer at any time (revoking the key) or by anyone after expiry; unspent deposit becomes consumer credit.

The supplier node serves `GET /v1/models` and `POST /v1/chat/completions` (OpenAI-compatible; `stream:true` returns the finished reply as one SSE chunk). Auth is `Authorization: Bearer <key>`; any browser origin may call `/v1`. Before each paid call the node reads the pass, checks the secret hash, expiry, provider, ceilings and per-call cap, and reserves the worst-case cost against the unspent deposit (concurrent calls cannot overspend). It charges on-chain after replying. A failed charge is the supplier's loss. The trust tradeoff versus per-request escrow: the supplier meters tokens without a per-call consumer signature, bounded by the deposit, per-call cap, price ceilings and expiry. Private mode does not use passes.

## Lit private protocol and hardware enforcement

`PeerRegistry.privacyVerifier()` is unset until independent authority installs the fixed `ZkDcapGatewayVerifier` once with reviewed runtime measurements, minimum Intel TCB counter, escrow and revoker. Suppliers cannot choose arbitrary proof verifiers. `setPrivacyConfig(bytes32)` accepts a nonzero canonical privacy configuration only with valid hardware/action/key evidence for the current provider/operator. `isPrivacyVerified(provider,configHash,escrow)` and `privacyEncryptionKeyHash` expose validity and the public HPKE fingerprint. A zero hash disables selection. Published hashes/fingerprints are not attestation by themselves.

The verifier checks a RISC Zero Groth16 proof of pinned zkDCAP execution rooted in Intel, exact TDX measurements, non-debug STATUS_OK, no advisories, collateral validity and current TCB floor. A one-use ten-minute challenge must be bound in authenticated REPORTDATA to chain, verifier, registry, escrow, provider/operator, configuration, immutable action ID, action/HPKE key hashes and TLS certificate hash. Accepted gateway leases are at most one hour/collateral expiry; revocations are permanent. **Current Lit evidence does not implement this binding and cannot register a gateway.** Full details and exact binary encodings: [on-chain attestation](docs/ONCHAIN_ATTESTATION.md).

`fundPrivate(offerId,promptCommitment,expiresAt,configHash)` retains existing escrow cap/rate/refund behavior and snapshots `requestPrivacyConfig`, `requestPrivacyOperator`, `requestEncryptionKeyHash`. It rejects invalid/unverified/revoked/expired/mismatched configuration. `claimPrivate(requestId,maxOutputTokens,contextHash,consumerSignature)` checks the current hardware record, funding key/operator, one-shot state and the consumer's EIP-712 `PrivateInferenceRequest(uint256 requestId,bytes32 promptHash,uint256 maxOutputTokens,bytes32 contextHash,bytes32 enclaveKeyHash)`. It stores `requestPrivateSession`; the successful transaction precedes any private paid API call. It is not proof of a particular inference execution.

The browser's signed session/HPKE AAD binds both wallets and keys, chain/contracts, offer/request, immutable action/configuration, prompt commitment, output limit, random challenge and issuance time. Consumer-side TDX/collateral/governance and TLS pinning remain required. The local helper's `/privacy/attest` route returns a verified-channel action key binding; that action signature alone is not hardware attestation. Request/response HPKE uses RFC9180 P256/HKDF-SHA256/AES256-GCM with direction separation. No supplier endpoint or mutable action can request plaintext or exported keys.

Private prompt/response hashes are secret-salted, configuration-bound commitments rather than plain content hashes. Private invoice shape adds `responseSalt`, visible only inside the encrypted answer. The existing operator Invoice and consumer UsageReceipt types are unchanged; settlement publishes only usage, commitment and payment metadata. Salts, plaintext and private keys never go on-chain. The immutable action also pins a secret-salted API credential commitment and official per-adapter origins; unsupported account policies and compatible endpoints are blocked. See [complete private protocol/setup](docs/PRIVACY.md).

Existing plain HTTP routes refuse privately funded requests. Private mode never falls back to them. The local test harness and mock verifier work only in explicit simulations; no simulation establishes hardware privacy. The public marketplace stays on Monad testnet 10143; third-party Lit KMS/governance uses Base and does not make Monad contracts an encryption/KMS system.

## Local account management (separate from the peer protocol)

The loopback-only account helper uses a one-use wallet-signed EIP-712 `LocalAccountAccess` challenge binding persisted helper service ID, configured origin, random challenge, expiry and management purpose. Its domain is `LLMProvidersLocalAccounts`, version `1`, chain `10143`, zero verifying contract; the resulting ten-minute bearer session remains in browser/helper memory. It cannot authorize inference, escrow settlement or on-chain publication. `npm run dev` also starts the helper. A fresh empty directory can pin its first management owner only through an explicit initialization-purpose signature and atomic owner check; unsigned claims and existing unowned credentials cannot use this route. Configured or saved owners remain pinned across restarts.

API-key save/list/remove returns masked, inference-unverified metadata and opaque owner-bound refs. Official OpenAI save with `discoverModels:true` retrieves only `/v1/models` metadata and binds one key/ref to the returned exact supported text model configs; manual saves perform no vendor call. Capabilities are checked separately from catalog visibility, which never proves inference/credit eligibility. Explicit rediscovery uses only a ref, invalidates old membership and clears models on failure. Removed/mismatched/unsupported refs block paid calls without environment fallback; cancellation/removal cannot resurrect a late cache. API secrets and OAuth tokens occupy separate owner-only files, with no vendor-secret-return/token-import endpoint.

ChatGPT consent uses official dynamic/issued app registration, S256 PKCE, fresh state/nonce and cryptographically verified OIDC identity/scopes. Personal Responses streaming returns success only after valid `response.completed`; it creates no signed marketplace invoice or funding request. Claude OAuth, supplier subscription resale and Lit private OAuth are rejected before credentials can be accessed. The supplier core rejects OAuth even with valid on-chain funding. Full HTTP schemas, statuses and live-service prerequisites: [ACCOUNT_CONNECTORS.md](docs/ACCOUNT_CONNECTORS.md).
